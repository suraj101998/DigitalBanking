Chapter 1  –  Abstract

This report presents the design, architecture, implementation, and evaluation of DigitalBanking — a production-grade REST API backend for a digital banking platform, built using Spring Boot 3.4 and Java 17. The project addresses the critical shortcomings commonly found in learning-level banking applications — namely, the use of primitive data types for monetary values, the absence of concurrent transaction safety, lack of idempotency, and weak security postures — by applying production engineering principles throughout the design and implementation phases.

The application provides a comprehensive suite of banking operations including customer account management, real-time credit and debit transactions, atomic fund transfers between accounts, JWT-based authentication with refresh token rotation, role-based access control, account lockout after repeated failed login attempts, and per-IP rate limiting using the Bucket4j token-bucket algorithm. All monetary values are stored and computed using BigDecimal with DECIMAL(19,4) precision at the database level, ensuring exact arithmetic without floating-point rounding errors.

Concurrent transaction correctness is guaranteed through a dual-locking strategy: pessimistic locking (SELECT FOR UPDATE via Spring Data JPA) prevents lost-update race conditions on bank account balances, while optimistic locking (Hibernate @Version) provides a last-resort safety net against concurrent modifications. Fund transfers between two accounts are made deadlock-safe by acquiring database row locks in ascending account-ID order, preventing the classic A→B / B→A circular wait scenario.

The persistence layer is managed using MySQL 8 with Flyway database migrations, replacing unreliable Hibernate DDL auto-generation with a version-controlled schema. Observability is provided through Micrometer metrics (exposed as Prometheus endpoints), SLF4J structured logging with per-request correlation IDs via MDC, and Spring Boot Actuator. The application includes a comprehensive test suite comprising 38 tests across unit, repository slice, security, and Testcontainers-based integration test categories.

The practical significance of this project lies in its direct applicability to the fintech industry. The patterns demonstrated — idempotent payment APIs, pessimistic locking for financial ledgers, JWT lifecycle management, and infrastructure-as-code deployment on AWS — are used at scale by production banking systems at institutions such as Razorpay, Paytm, and HDFC Bank's digital division.

Chapter 2  –  Project Description

2.1 Project Overview and Motivation

The DigitalBanking project is a modular monolith REST API backend for a digital banking platform. It was conceived and built to demonstrate how the theoretical concepts taught in the Scaler Neovarsity Master's program — system design, database modeling, concurrent programming, security engineering, and cloud deployment — translate into a single, coherent, production-quality software product.

Banking backends occupy a uniquely demanding position in software engineering. Unlike a typical e-commerce or social media API, a banking system cannot tolerate approximate arithmetic (floating-point money), optimistic assumptions about concurrent access, stateless balance derivation from transaction history, or a missing idempotency layer. A ₹10,000 debit that is processed twice due to a network retry is not a UX problem; it is a regulatory liability. The motivation for this project was to build a system where these failure modes are structurally impossible, not merely "unlikely."

The project was designed as a GitHub-hosted, interview-grade Spring Boot application — a codebase that demonstrates mastery of the backend specialization curriculum: Spring Boot, JPA/Hibernate, Spring Security, REST API design, database engineering, observability, and testing. It is intended to serve as both a learning artefact and a portfolio piece that communicates a coherent backend engineering story.

2.2 Project Objectives

The following objectives guided every architectural and implementation decision made in this project:

  • Financial Correctness: Eliminate all floating-point arithmetic from monetary calculations. Use BigDecimal with DECIMAL(19,4) column precision universally. The balance of a bank account must always be a first-class, database-level state — never derived from summing transaction history at query time.
  • Concurrency Safety: Design every balance-modifying operation to be safe under concurrent HTTP requests. A debit of ₹8,000 and a simultaneous debit of ₹7,000 from a ₹10,000 account must never both succeed. This requires database-level locking, not just application-level checks.
  • Idempotent Payment API: Any payment or transfer endpoint must be safe to retry without risk of double-processing. A client that retries a payment after a network timeout must receive the same response as the original request, not a duplicate charge.
  • Secure Authentication Lifecycle: Implement JWT access tokens (1-hour expiry) with refresh token rotation (7-day expiry), account lockout after 5 consecutive failed login attempts, and per-IP rate limiting to protect authentication endpoints from brute-force attacks.
  • Production-Grade Database Design: Replace Hibernate ddl-auto=update with Flyway version-controlled migrations. Enforce foreign key constraints, unique constraints, and composite indexes where required by query patterns.
  • Comprehensive Observability: All requests must carry a correlation ID traceable through logs. Micrometer counters and timers must expose transaction success/failure metrics to Prometheus for visualization in Grafana.
  • Serious Test Coverage: Unit tests for all service logic, repository slice tests against H2, and full-stack integration tests against a real MySQL container using Testcontainers.

5.13 BigDecimal Financial Precision

All monetary columns use DECIMAL(19,4) in MySQL, mapped to java.math.BigDecimal in Java with precision=19, scale=4 in the JPA @Column annotation. This choice has three important consequences:

  1. No floating-point error: DECIMAL is an exact numeric type in SQL, unlike FLOAT or DOUBLE. A transfer of ₹100.00 will always result in a balance difference of exactly ₹100.00, never ₹99.99999999 due to IEEE 754 rounding.
  2. Four decimal places: Indian Rupee values require at most two decimal places (paise), but four are retained for compatibility with foreign currency operations and to avoid truncation errors when applying interest rates.
  3. Java arithmetic: All balance arithmetic in the service layer uses BigDecimal.subtract() and BigDecimal.add() rather than primitive long or double arithmetic. The comparison to detect insufficient funds uses currentBalance.compareTo(amount) < 0, which respects BigDecimal's scale.

6.2.3 Pessimistic Locking Implementation

When this method is called inside a @Transactional service method, Hibernate translates it to SELECT … FOR UPDATE in MySQL. 6.4 Feature 2: Atomic Fund Transfer

6.4.1 The Deadlock Problem

Fund transfers involve two account balance updates that must both succeed or both fail. The naive implementation acquires locks on account A then account B. A concurrent transfer in the opposite direction (B→A) acquires B then A. If both transactions execute simultaneously, each holds the lock the other needs, producing a deadlock. MySQL will detect the deadlock and roll back one transaction with ER_LOCK_DEADLOCK, but the client receives an error rather than a transparent retry.

The deadlock-safe solution is to always acquire the two locks in the same global order regardless of the direction of transfer. The canonical order chosen is ascending account_id:

// TransferServiceImpl.java — deadlock-safe lock ordering
BankAccount first  = source.getId() < dest.getId() ? source : dest;
BankAccount second = source.getId() < dest.getId() ? dest   : source;

BankAccount lockedFirst = bankAccountRepository
    .findByCustomerIdForUpdate(first.getCustomerId())
    .orElseThrow(() -> new AccountNotFoundException(first.getCustomerId()));
BankAccount lockedSecond = bankAccountRepository
    .findByCustomerIdForUpdate(second.getCustomerId())
    .orElseThrow(() -> new AccountNotFoundException(second.getCustomerId()));

// Re-map locked instances back to source/dest
BankAccount lockedSource = lockedFirst.getId().equals(source.getId())
    ? lockedFirst : lockedSecond;
BankAccount lockedDest = lockedFirst.getId().equals(dest.getId())
    ? lockedFirst : lockedSecond;
Code Snippet 6.5 – Deadlock-safe lock acquisition in ascending account_id order

With this ordering, a transfer A(id=1)→B(id=2) and a concurrent B(id=2)→A(id=1) will both attempt to acquire the lock on id=1 first. The second one will block at the database level until the first completes, eliminating the deadlock entirely.

6.5 Feature 3: Idempotent Request Handling

6.5.1 The Double-Charge Problem

Mobile and web banking clients operate over unreliable networks. When a payment request times out, the client cannot know whether the server processed the request before the timeout occurred. If the client simply retries, it risks creating a duplicate payment. The idempotency mechanism eliminates this risk by allowing safe retries: a request with an already-seen key will always return the same response that was returned for the original request, without executing the operation again.

6.6 Feature 4: Transaction Reversal

The reversal endpoint POST /api/v1/transactions/{id}/reverse allows an ADMIN user to reverse a previously committed SUCCESS transaction. The reversal process performs the opposite balance operation: if the original was a DEBIT, a compensating CREDIT is applied; if a CREDIT, a DEBIT is applied.

The original transaction record's transactionStatus field is updated from SUCCESS to REVERSED. This is the only permitted post-commit modification, allowed specifically because it is a status transition rather than a financial value change. The @PreUpdate hook in Transactions.java ensures that attempts to modify amount, type, or customer reference on a committed record will not silently persist.

6.9 Rate Limiting with Bucket4j

7.7 Scaling Strategy

The pool name DigitalBankingPool is exposed through JMX and Micrometer, allowing pool saturation (waiting connections) and connection acquisition time to be monitored in production dashboards.

8.9 Bucket4j 8.10.1

Bucket4j is a thread-safe, Java-native implementation of the token-bucket rate limiting algorithm, based on the Bucket4j library by Vladimir Bukhtoyarov. The token-bucket algorithm is superior to simpler fixed-window counters for rate limiting because it handles burst traffic gracefully: a client that sends 50 requests at the start of a minute and then pauses will have its bucket refilled for the next burst, rather than being hard-blocked until the window resets.

8.9.1 Application in DigitalBanking

The RateLimitingFilter creates one Bucket instance per client IP, stored in a ConcurrentHashMap. Each bucket has a capacity of 100 tokens and a greedy refill rate of 100 tokens per minute. The Bandwidth.builder().refillGreedy() method fills the bucket continuously throughout the minute rather than adding all 100 tokens at the start of each minute, which prevents coordinated burst attacks at minute boundaries.

Bucket4j 8.10.1 was specifically chosen over earlier versions because it removes the deprecated Bandwidth.classic() constructor and replaces it with the fluent builder API, which is compatible with Java 17 module restrictions.

8.10 Micrometer and Prometheus

Micrometer is the application metrics facade for Spring Boot, analogous to SLF4J for logging. It provides a vendor-neutral API (Counter, Timer, Gauge) that can be backed by any metrics system: Prometheus, Datadog, CloudWatch, New Relic, or others. The DigitalBanking application uses the Prometheus backend via the micrometer-registry-prometheus dependency.

Prometheus scrapes the /actuator/prometheus endpoint at regular intervals (typically every 15 seconds) and stores time-series data. Grafana queries Prometheus to render dashboards showing real-time and historical transaction rates, P99 latency, error rates, and HikariCP pool utilization.

9.1 Project Summary

This project undertook a comprehensive redesign and improvement of the DigitalBanking Spring Boot backend application, transforming it from a prototype-grade codebase with significant financial correctness, security, and architectural deficiencies into a production-ready banking API that adheres to industry best practices.

The work addressed 87 specific improvement items organised across six phases: financial correctness, architecture, security, database management, testing, and observability. 9.2 Key Technical Achievements

9.2.1 Financial Correctness

The most critical improvements were in financial correctness. The original codebase stored monetary amounts as long integers and derived the current balance from the most recent transaction record — both practices that introduce data loss in production banking systems. The redesigned system stores all monetary values as DECIMAL(19,4) in MySQL and java.math.BigDecimal in Java, with a dedicated bank_accounts table as the single source of truth for the current balance. Race conditions that could cause two concurrent transactions to both read the same balance and produce incorrect results are eliminated through pessimistic write locking (SELECT FOR UPDATE) and optimistic locking (@Version).

9.2.2 Security

The security architecture was rebuilt from scratch: structured JWT claims with issuer and audience validation, BCrypt password hashing, refresh token rotation with server-side revocation, account lockout after five failed attempts, rate limiting at 100 requests per minute per IP, and least-privilege URL-based authorization rules. Sensitive configuration values (JWT secret, database credentials) are externalized as environment variables backed by AWS Secrets Manager in production, never hardcoded in source files.

9.2.3 Architecture

The architectural improvements follow the SOLID principles and clean architecture patterns expected of production Java enterprise applications: constructor injection replaces field injection throughout, domain-specific exceptions replace generic RuntimeException usage, response DTOs replace direct entity serialization, and a global exception handler provides consistent, structured error responses with HTTP status codes, trace IDs, and machine-readable error bodies. The AOP logging aspect provides method-level tracing without the cross-cutting concern polluting business logic.

9.2.4 Testability

The 38-test suite provides coverage at three levels: unit tests for service logic with Mockito mocks, repository tests against H2 in-memory databases with @DataJpaTest, and end-to-end integration tests against real MySQL using Testcontainers. The use of constructor injection (rather than field injection) is what makes the unit tests possible: Mockito cannot inject @Autowired field mocks into a class that requires a running Spring context, but can trivially pass mock objects to a constructor.

9.3 Practical Applications

The patterns implemented in this project are directly applicable to production banking and fintech systems:

  • Idempotency keys are used by Stripe, Razorpay, and virtually every financial API to allow safe client retries. The implementation pattern demonstrated here (check key → process → store response → return) is the canonical approach.
  • Deadlock-safe lock ordering is a standard technique in databases and operating systems. The min-ID-first approach used in the transfer service is equivalent to the algorithm used by database engines themselves to prevent deadlocks during page locking.
  • Token rotation with server-side storage is the recommended approach for refresh tokens in the OAuth 2.0 Security Best Current Practice specification, providing a defence against token theft.
  • Rate limiting with token buckets is the algorithm used by Cloudflare, nginx (limit_req), and AWS API Gateway for request throttling.
  • Flyway migrations are used by companies including Netflix, GitHub, and Atlassian to manage database schema changes in CI/CD pipelines.

9.4 Limitations and Known Constraints

The following limitations are acknowledged and represent areas for future improvement:

9.4.1 Rate Limiting Scalability

The current RateLimitingFilter stores per-IP rate-limit buckets in a ConcurrentHashMap in the JVM heap. This is correct for a single-node deployment but does not distribute rate limit state across multiple EC2 instances in the Elastic Beanstalk Auto Scaling Group. A user could circumvent the limit by having their requests routed to different instances by the load balancer. Production-grade multi-node rate limiting requires a Redis-backed distributed bucket store using the Bucket4j Redis extension (bucket4j-redis).

9.4.2 Spring Cache: Simple Provider

The current cache implementation uses spring.cache.type=simple, which stores cached objects in a ConcurrentHashMap in the JVM heap. Like the rate limiter, this does not share cache state across instances, meaning each instance builds its own cache from scratch. In a multi-node deployment, cache invalidation (when a customer is updated) only clears the cache on the instance that processed the update request. Upgrading to spring.cache.type=redis with a shared ElastiCache Redis cluster would provide consistent cache invalidation across all instances.

9.4.3 HMAC-SHA256 vs RSA JWT Signing

The JWT is signed with HMAC-SHA256 (symmetric), meaning the same secret key is used for both signing and verification. This is appropriate for a monolithic application where only one service generates and verifies tokens. However, in a microservices architecture where different services need to independently verify tokens without having access to the signing secret, RSA (RS256) or ECDSA (ES256) asymmetric signing would be preferable: the private key signs tokens and only the corresponding public key is needed for verification.

9.4.4 Missing Daily and Monthly Transaction Limit Enforcement

The TransactionLimitConfig defines daily and monthly transaction limits (banking.transaction.daily-limit=1000000, banking.transaction.monthly-limit=5000000) but the current service implementation only enforces the per-transaction limit. A complete implementation would require a query aggregating the sum of a customer's transactions within the current calendar day/month before allowing a new transaction, which is omitted from the current scope.

9.4.5 Two-Factor Authentication

Banking-grade security typically requires two-factor authentication (2FA) for high-value transactions or login from a new device. The current implementation provides username/password authentication with JWT but does not implement OTP, TOTP, or push notification 2FA. This is acknowledged as a future enhancement.
