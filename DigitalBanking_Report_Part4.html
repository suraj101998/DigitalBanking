6.1 Overview

This chapter documents the implementation of the four core banking features, describing the full request-to-response lifecycle for each: (1) payment processing (credit/debit), (2) atomic fund transfer between accounts, (3) idempotent retry handling, and (4) transaction reversal. 6.2.3 Pessimistic Locking Implementation

The key to financial correctness in payment processing is the pessimistic write lock acquired on the BankAccount row before any balance read-modify-write. The relevant repository method is:

// BankAccountRepository.java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT b FROM BankAccount b WHERE b.customerId = :customerId")
Optional<BankAccount> findByCustomerIdForUpdate(@Param("customerId") int customerId);
Code Snippet 6.1 – Pessimistic write lock on BankAccount row

When this method is called inside a @Transactional service method, Hibernate translates it to SELECT … FOR UPDATE in MySQL. The database engine places a row-level exclusive lock on the matching bank_accounts row. Any concurrent transaction that attempts to read the same row with FOR UPDATE will block at the database level until the first transaction commits or rolls back. This is the correct mechanism for preventing lost-update races in a high-concurrency banking system.

6.2.4 Balance Arithmetic

The balance update logic in TransactionServiceImpl.doCreateTransaction() uses BigDecimal arithmetic exclusively:

// TransactionServiceImpl.java — balance calculation
BigDecimal currentBalance = account.getBalance();

BigDecimal newBalance;
if (type == TransactionType.DEBIT) {
    if (currentBalance.compareTo(transactionAmount) < 0) {
        txInsufficientBalanceCounter.increment();
        txFailureCounter.increment();
        throw new InsufficientBalanceException(
            "Insufficient balance. Current: " + currentBalance
            + ", Requested: " + transactionAmount);
    }
    newBalance = currentBalance.subtract(transactionAmount);
} else {
    newBalance = currentBalance.add(transactionAmount);
}
account.setBalance(newBalance);
bankAccountRepository.save(account);
Code Snippet 6.2 – BigDecimal balance arithmetic with insufficient-balance check

The compareTo method is used for comparison rather than equals, because BigDecimal.equals considers scale in its comparison (i.e., 100.00.equals(100.0) returns false). The subtract and add methods produce exact results without the floating-point approximation errors that would arise from double arithmetic.

6.2.5 Immutable Ledger Record

After the balance is updated, an immutable Transactions ledger record is saved with two balance snapshots:

  • initialDeposit — the balance before the transaction was applied
  • availableBalance — the balance after the transaction was applied

These snapshots serve as an audit trail independent of the BankAccount.balance field. Even if the account balance were ever corrupted, these ledger snapshots allow every historical balance to be reconstructed from the transaction sequence. The @Version field on Transactions prevents any post-commit modification of the amount, type, or customer reference.

6.4 Feature 2: Atomic Fund Transfer

6.4.1 The Deadlock Problem

Fund transfers involve two account balance updates that must both succeed or both fail. The naive implementation acquires locks on account A then account B. A concurrent transfer in the opposite direction (B→A) acquires B then A. If both transactions execute simultaneously, each holds the lock the other needs, producing a deadlock. MySQL will detect the deadlock and roll back one transaction with ER_LOCK_DEADLOCK, but the client receives an error rather than a transparent retry.

The deadlock-safe solution is to always acquire the two locks in the same global order regardless of the direction of transfer. The canonical order chosen is ascending account_id:

// TransferServiceImpl.java — deadlock-safe lock ordering
BankAccount first  = source.getId() < dest.getId() ? source : dest;
BankAccount second = source.getId() < dest.getId() ? dest   : source;

BankAccount lockedFirst = bankAccountRepository
    .findByCustomerIdForUpdate(first.getCustomerId())
    .orElseThrow(() -> new AccountNotFoundException(first.getCustomerId()));
BankAccount lockedSecond = bankAccountRepository
    .findByCustomerIdForUpdate(second.getCustomerId())
    .orElseThrow(() -> new AccountNotFoundException(second.getCustomerId()));

// Re-map locked instances back to source/dest
BankAccount lockedSource = lockedFirst.getId().equals(source.getId())
    ? lockedFirst : lockedSecond;
BankAccount lockedDest = lockedFirst.getId().equals(dest.getId())
    ? lockedFirst : lockedSecond;
Code Snippet 6.5 – Deadlock-safe lock acquisition in ascending account_id order

With this ordering, a transfer A(id=1)→B(id=2) and a concurrent B(id=2)→A(id=1) will both attempt to acquire the lock on id=1 first. The second one will block at the database level until the first completes, eliminating the deadlock entirely.

6.4.2 Dual Ledger Entries

A successful transfer creates two independent transaction records: a DEBIT entry against the source account and a CREDIT entry against the destination account. Both entries carry the same Instant timestamp, a globally unique transferId prefix (TRF), and if an idempotency key was provided, suffixed variants ({iKey}-debit and {iKey}-credit) to maintain deduplication coverage for both legs.

6.4.3 Transfer Atomicity

The entire transfer — locking both accounts, updating both balances, saving both ledger entries, and persisting the idempotency record — executes within a single Spring @Transactional boundary on TransferServiceImpl.transfer(). If any step throws an exception (including the ObjectOptimisticLockingFailureException from the @Version check), the transaction manager rolls back all changes. 6.5 Feature 3: Idempotent Request Handling

6.5.1 The Double-Charge Problem

Mobile and web banking clients operate over unreliable networks. When a payment request times out, the client cannot know whether the server processed the request before the timeout occurred. If the client simply retries, it risks creating a duplicate payment. The idempotency mechanism eliminates this risk by allowing safe retries: a request with an already-seen key will always return the same response that was returned for the original request, without executing the operation again.

6.6 Feature 4: Transaction Reversal

The reversal endpoint POST /api/v1/transactions/{id}/reverse allows an ADMIN user to reverse a previously committed SUCCESS transaction. The reversal process performs the opposite balance operation: if the original was a DEBIT, a compensating CREDIT is applied; if a CREDIT, a DEBIT is applied.

The original transaction record's transactionStatus field is updated from SUCCESS to REVERSED. This is the only permitted post-commit modification, allowed specifically because it is a status transition rather than a financial value change. The @PreUpdate hook in Transactions.java ensures that attempts to modify amount, type, or customer reference on a committed record will not silently persist.

6.8 Account Lockout Implementation

The User entity implements the account lockout logic directly in the domain model through two methods: recordFailedLogin() and recordSuccessfulLogin(). This avoids spreading lockout logic across the service layer and keeps the policy co-located with the data it manages.

// User.java
public void recordFailedLogin() {
    this.failedLoginAttempts++;
    if (this.failedLoginAttempts >= MAX_FAILED_ATTEMPTS) {  // 5
        this.lockedUntil = Instant.now().plusSeconds(
            LOCK_DURATION_MINUTES * 60L);                   // +15 min
    }
}

public boolean isAccountLocked() {
    return lockedUntil != null && Instant.now().isBefore(lockedUntil);
}
Code Snippet 6.9 – Account lockout logic in the User domain entity

The AuthenticationController calls recordFailedLogin() whenever Spring Security's AuthenticationManager.authenticate() throws BadCredentialsException, and calls recordSuccessfulLogin() on every successful login. The resulting state is persisted by saving the User entity after each attempt.

6.9 Rate Limiting with Bucket4j

The RateLimitingFilter implements a token-bucket rate limiter using Bucket4j 8.10.1. Each unique client IP address gets its own bucket with a capacity of 100 tokens, refilled at a rate of 100 tokens per minute (greedy refill). The buckets are stored in a ConcurrentHashMap, which is correct for single-node deployments. For a multi-node deployment, the map would need to be replaced with a Redis-backed distributed cache using Bucket4j's Redis extension.

// RateLimitingFilter.java
private Bucket createBucket() {
    Bandwidth limit = Bandwidth.builder()
        .capacity(capacity)             // 100
        .refillGreedy(capacity, period) // 100 per minute
        .build();
    return Bucket.builder().addLimit(limit).build();
}

public void doFilter(...)  {
    String ip = resolveClientIp(httpReq);
    Bucket bucket = buckets.computeIfAbsent(ip, k -> createBucket());
    if (bucket.tryConsume(1)) {
        chain.doFilter(req, res);
    } else {
        httpRes.setStatus(429);         // Too Many Requests
        httpRes.getWriter().write("{\"status\":429,...}");
    }
}
Code Snippet 6.10 – Bucket4j token-bucket rate limiting by client IP

Chapter 7: Deployment Flow and Architecture

7.1 Deployment Overview

The DigitalBanking application is designed for deployment on Amazon Web Services (AWS), leveraging managed services to achieve high availability, elastic scalability, and operational simplicity. The deployment architecture separates compute, database, caching, and network layers, following the AWS Well-Architected Framework's principles of operational excellence, security, reliability, performance efficiency, and cost optimisation.

The Spring Boot application is packaged as a self-contained executable JAR (mvn package -DskipTests) and deployed to AWS Elastic Beanstalk, which manages the EC2 instances, load balancer, auto-scaling group, and rolling deployments automatically. The database is hosted on Amazon RDS for MySQL 8.0 with Multi-AZ deployment for automatic failover.

7.7 Scaling Strategy

Elastic Beanstalk is configured with an Auto Scaling Group spanning a minimum of two EC2 instances (for high availability across two Availability Zones) and a maximum of six instances. Scaling triggers are based on CloudWatch metrics:

  • Scale out: Average CPU utilisation > 70% for 5 minutes → add 2 instances
  • Scale in: Average CPU utilisation < 30% for 15 minutes → remove 1 instance

The application is horizontally scalable because it is stateless: all session state is in JWT tokens (client-side) or the database (refresh tokens, idempotency keys). The one stateful component in the current implementation is the ConcurrentHashMap in RateLimitingFilter, which does not share rate-limit state across instances. This would need to be upgraded to a Redis-backed bucket for accurate rate limiting in a multi-node deployment.

7.8 Database High Availability

Amazon RDS MySQL is configured with Multi-AZ deployment. The primary DB instance synchronously replicates to a standby instance in a second Availability Zone. If the primary instance fails due to hardware, network, or software issues, RDS automatically promotes the standby within 1–2 minutes without manual intervention. The JDBC endpoint is a DNS CNAME that automatically points to the current primary instance, making the failover transparent to the application.

Automated backups are retained for 7 days, and manual DB snapshots are taken before each major deployment. The performance_schema database in MySQL 8 is monitored through Amazon RDS Performance Insights to identify slow queries and lock contention events in production.

7.9 Logging and Monitoring

Application logs are written to two destinations simultaneously:

  1. File system (./logs/trace_log.log) with daily rotation, 30-day retention, and 10 MB max file size (configured in logback-spring.xml and application.properties).
  2. CloudWatch Logs via the Elastic Beanstalk CloudWatch integration, enabling centralised log aggregation and alerting across all instances.

Every log line includes the %X{correlationId} MDC key, enabling end-to-end tracing of a single request across filter, service, and repository layers by searching CloudWatch Logs Insights for a single UUID. Tomcat access logs are also written in Combined Log Format, capturing HTTP method, URI, response status, response time, and user agent for every request.

7.12 Chapter Summary

Chapter 7 has presented the production deployment architecture for the DigitalBanking application on AWS. The key components are Elastic Beanstalk for managed application deployment, Amazon RDS MySQL Multi-AZ for highly available persistent storage, ElastiCache Redis for distributed caching, AWS Secrets Manager for credential management, and CloudWatch for centralised observability.
