Chapter 4: Class Diagrams and System Architecture

4.1 Introduction

This chapter presents the structural design of the DigitalBanking application through Unified Modelling Language (UML) class diagrams. These diagrams represent the entity layer, service layer, security filter chain, and repository abstractions as they are implemented in the production codebase. Every class, field, and relationship shown has a direct counterpart in the Java source files located under src/main/java/com/example/pi/.

The application follows a strict layered architecture: Controller → Service → Repository → Entity. Dependencies flow only downward; the entity layer has no dependency on any other layer. The security layer wraps the controller layer as a cross-cutting concern implemented through servlet filters registered in SecurityConfiguration.

4.6 Security Filter Chain Architecture

HTTP requests traverse a chain of servlet filters before reaching any Spring MVC controller. The chain is ordered as follows, from outermost to innermost:

  1. CorrelationIdFilter (Order 1) – Reads or generates an X-Correlation-Id UUID and stores it in SLF4J MDC so that every subsequent log line within the same request thread includes the trace identifier.
  2. RequestResponseLoggingFilter (Order −100) – Logs the HTTP method, URI, response status, and elapsed time for every request/response pair.
  3. RateLimitingFilter (Order −90) – Applies a Bucket4j token-bucket rate limit of 100 requests per minute per client IP. Requests exceeding the limit receive an HTTP 429 response immediately, before any authentication logic runs.
  4. JwtAuthenticationFilter – Extracts the Bearer token from the Authorization header, validates its signature and claims using JwtUtils, and populates the Spring Security SecurityContextHolder.
  5. UsernamePasswordAuthenticationFilter – Spring Security standard; bypassed for stateless JWT flow.

Chapter 5: Database Schema Design

5.1 Introduction

The database design underpins the financial correctness guarantees of the DigitalBanking application. This chapter documents every table, column, constraint, and index in the production schema as defined by the two Flyway migration scripts: V1__initial_schema.sql and V2__add_idempotency.sql. The database engine is MySQL 8 (InnoDB storage engine, utf8mb4 character set). H2 in-memory mode is used for the unit and repository test suite.

All financial amounts are stored as DECIMAL(19,4), which supports values up to 999,999,999,999,999.9999 with four decimal places, sufficient for Indian Rupee transactions with sub-paisa precision. Timestamps are stored as DATETIME(6), providing microsecond-level resolution mapped to Java's java.time.Instant.

Financial Correctness: Separating the account balance into a dedicated bank_accounts table with a version column resolves a critical race condition in the original schema where balance was derived from the most recent transaction record. Two concurrent transactions could each read the same "last balance," both subtract from it, and write back, resulting in a lost update. The version column ensures that the second writer will detect the stale version and fail with ObjectOptimisticLockingFailureException, which the service layer translates into a ConcurrentTransactionException and HTTP 409 to the client.

Immutable Ledger: Once a transaction record is persisted with status SUCCESS, only the transaction_status field may change (e.g., to REVERSED on a reversal request). The @PreUpdate hook in Transactions.java guards against accidental mutation of amount, type, or customer reference. The version column on the transactions table acts as a secondary optimistic lock — any attempt to modify an already-committed entry in a concurrent scenario will raise a conflict rather than silently overwrite the record.

Indexes: A composite index idx_transactions_customer_date (customer_id, transaction_date DESC) is created to support the most common query pattern: "give me all transactions for customer X, newest first." Without this index, MySQL would perform a full table scan over the transactions table for every pagination query, which becomes catastrophically slow as transaction volume grows.

5.6 Table: idempotency_keys

Table 5.05 – idempotency_keys Table Column Specifications
ColumnTypeConstraintsDescription
idBIGINTPK, AUTO_INCREMENTSurrogate primary key
idempotency_keyVARCHAR(64)NOT NULL, UNIQUEClient-supplied UUID or hash string
transaction_idVARCHAR(50)NULLReference to the transaction created by this key
response_statusINTNULLHTTP status code of the original response
response_bodyTEXTNULLJSON-serialized response body for replay
created_atDATETIME(6)NOT NULLTimestamp of original processing
customer_idINTNULLCustomer who submitted the original request

Idempotency Design: When a client sends a payment request with an Idempotency-Key header, the service first queries idempotency_keys by that key. If a matching row exists, the stored response_body is deserialized and returned immediately — the payment is not processed again. If no row exists, the payment is processed and a new row is inserted. This pattern protects against double charges caused by network timeouts where the client retries a request that actually succeeded on the first attempt. The UNIQUE constraint on idempotency_key ensures that even if two concurrent retry requests arrive simultaneously, only one INSERT will succeed; the other will receive a duplicate key error and fall back to reading the existing record.

Token Rotation: The UNIQUE constraint on user_id enforces a one-token-per-user policy. When a user calls POST /api/v1/auth/refresh, the existing refresh token is deleted and a new token is issued atomically within a single @Transactional boundary. This token rotation strategy prevents refresh token replay attacks: if a stolen refresh token is used, the legitimate user's subsequent refresh call will detect the missing token and re-authenticate from scratch.

5.9 Flyway Migration Timeline

Database schema changes are managed exclusively through Flyway versioned migration scripts. The schema is never modified directly or through Hibernate's hbm2ddl auto-DDL mechanism in non-development environments. This ensures that every environment (development, testing, staging, production) is running the identical schema version and that changes are tracked in version control alongside the application code.

Table 5.07 – Flyway Migration History
VersionFileDescriptionTables Affected
V1 V1__initial_schema.sql Creates the initial schema with five tables, all FK constraints, unique keys, and the composite index on transactions. customers, users, bank_accounts, transactions, refresh_tokens
V2 V2__add_idempotency.sql Creates the idempotency_keys table. Adds idempotency_key and version columns to transactions with a unique key on idempotency_key. idempotency_keys (new), transactions (altered)

The Flyway configuration uses spring.flyway.baseline-on-migrate=true so that an existing database (from ddl-auto=update local development) is baselined at V0 before V1 and V2 are applied, preventing the migration from failing on a non-empty database. In production the environment variable DB_FLYWAY_ENABLED=true must be set; in development spring.flyway.enabled defaults to false to keep local iteration fast.

5.13 BigDecimal Financial Precision

All monetary columns use DECIMAL(19,4) in MySQL, mapped to java.math.BigDecimal in Java with precision=19, scale=4 in the JPA @Column annotation. This choice has three important consequences:

  1. No floating-point error: DECIMAL is an exact numeric type in SQL, unlike FLOAT or DOUBLE. A transfer of ₹100.00 will always result in a balance difference of exactly ₹100.00, never ₹99.99999999 due to IEEE 754 rounding.
  2. Four decimal places: Indian Rupee values require at most two decimal places (paise), but four are retained for compatibility with foreign currency operations and to avoid truncation errors when applying interest rates.
  3. Java arithmetic: All balance arithmetic in the service layer uses BigDecimal.subtract() and BigDecimal.add() rather than primitive long or double arithmetic. The comparison to detect insufficient funds uses currentBalance.compareTo(amount) < 0, which respects BigDecimal's scale.

4.9 Aspect-Oriented Logging

A Spring AOP aspect, LoggingAspect, provides cross-cutting method-entry and method-exit logging for all classes in the com.example.pi package. A single @Around pointcut intercepts every public method in the service, repository, and controller layers. The aspect redacts sensitive arguments — specifically those whose parameter names contain the words password, token, or secret — replacing the value with the string [REDACTED] in the log output.

This prevents accidental logging of credentials while still providing full method tracing. All log lines produced by the aspect carry the MDC correlationId key set by CorrelationIdFilter, enabling end-to-end request tracing across service calls by searching log files for a single UUID.

Production observability is implemented through three complementary mechanisms, shown in Figure 4.4:

The four Micrometer instruments registered in TransactionServiceImpl are:

  • transaction.success.count — incremented on every successfully committed transaction
  • transaction.failure.count — incremented on any exception that aborts a transaction
  • transaction.insufficient_balance.count — incremented specifically on InsufficientBalanceException for fraud/anomaly alerting

These metrics are exposed at /actuator/prometheus in Prometheus text format and are secured to require ROLE_ADMIN except for /actuator/health and /actuator/info.
