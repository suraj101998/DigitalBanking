8.2 Java 17 (Eclipse Temurin LTS)

Java 17 is the Long-Term Support release that serves as the language and runtime foundation for the entire application. The choice of Java 17 over older versions is motivated by three factors: it is the minimum required by Spring Boot 3, it introduces the sealed class and record language features that are used in newer Spring Data and Jackson integrations, and it will receive security patches until September 2029, providing a stable foundation for production banking software.

The Eclipse Temurin distribution (formerly AdoptOpenJDK) is used rather than Oracle JDK because it is a fully open-source, TCK-certified build with no commercial licensing restrictions, making it suitable for all deployment environments including AWS EC2 and container images.

8.2.1 Project Application

The project uses Java 17 features throughout: var type inference for local variables (e.g., var existing = idempotencyKeyRepository.findByIdempotencyKey(iKey)), the enhanced switch expression, Optional.orElseThrow() with lambda constructors, and text block-style stream pipelines. The Maven compiler is configured with <source>17</source> and <target>17</target> in pom.xml.

8.3 Spring Boot 3

Spring Boot 3 is the application framework that provides the runtime container, autoconfiguration, dependency injection, and integrated management for the application. It is built on top of the Spring Framework 6 and requires Java 17 as the minimum runtime version.

8.3.1 Key Features Used

  • Embedded Tomcat: The application runs as a self-contained executable JAR with an embedded Tomcat 10.1 server. No separate application server installation is required for deployment.
  • Autoconfiguration: Spring Boot automatically configures JPA, HikariCP, Spring Security, Flyway, and Spring Cache based on the dependencies present on the classpath and the properties in application.properties.
  • @ConfigurationProperties: The JwtConfig and TransactionLimitConfig classes use @ConfigurationProperties to bind typed configuration from application.properties, replacing scattered @Value annotations with a single validated configuration object.
  • Spring Actuator: The Actuator module exposes operational endpoints (/actuator/health, /actuator/metrics, /actuator/prometheus) with fine-grained security control.
  • Spring Data Web: Pagination parameters (page, size, sort) are automatically resolved from HTTP query parameters to Pageable objects through Spring Data Web support.

8.4 Spring Data JPA / Hibernate 6

Spring Data JPA provides the repository abstraction layer, allowing the developer to declare query methods by naming convention or @Query annotation without writing JDBC boilerplate. Hibernate 6 is the JPA provider that translates entity operations and JPQL queries to SQL statements.

8.4.1 Key Features Used

  • JpaRepository: All five repository interfaces extend JpaRepository<T, ID>, inheriting standard CRUD, pagination, and sorting operations.
  • @Lock(PESSIMISTIC_WRITE): The findByCustomerIdForUpdate method in BankAccountRepository acquires SELECT … FOR UPDATE database locks, essential for preventing lost-update race conditions in concurrent balance modifications.
  • @Version: Applied to the version field of both BankAccount and Transactions entities to enable optimistic concurrency control. Hibernate automatically increments the version on every UPDATE and throws ObjectOptimisticLockingFailureException if the row was modified by another transaction since the entity was read.
  • @Transactional: Service methods are annotated with @Transactional to demarcate transaction boundaries. Read-only service methods use @Transactional(readOnly=true), which enables Hibernate's performance optimisations for read-only persistence contexts.
  • @Enumerated(STRING): Enum columns are stored as their string name rather than ordinal, making the database human-readable and resilient to reordering of enum values.

8.5 Spring Security 6

Spring Security 6 provides the authentication and authorization infrastructure. The configuration uses the lambda-style DSL introduced in Spring Security 6, which is more readable and avoids the deprecated WebSecurityConfigurerAdapter pattern.

8.5.1 Key Features Used

  • Stateless JWT sessions: SessionCreationPolicy.STATELESS disables server-side session management. Every request must carry a valid JWT in the Authorization header.
  • @EnableMethodSecurity: Enables @PreAuthorize and role-based method security annotations as a complement to URL-based authorization rules.
  • HttpMethod-based matchers: URL authorization rules specify the HTTP method separately (e.g., POST /api/v1/customers requires ADMIN but GET /api/v1/customers/{id} allows USER), implementing least-privilege access control.
  • BCryptPasswordEncoder: All passwords are hashed with BCrypt (work factor 10 by default), which is computationally expensive to brute-force and includes a random salt in every hash.

8.6 JJWT (Java JWT) 0.12.x

JJWT is the industry-standard Java library for creating and parsing JSON Web Tokens conforming to RFC 7519. Version 0.12.x introduces a fluent builder API that is type-safe and removes the deprecated string-based signing methods.

8.6.1 Key Features Used

  • Jwts.builder(): Constructs JWT with subject, issuer, audience, custom claims (roles, customerId), issuedAt, expiration, and HMAC-SHA256 signature.
  • Jwts.parser(): Parses and verifies JWT signature using the same secret key; throws JwtException subclasses for expired, malformed, or tampered tokens.
  • Keys.hmacShaKeyFor(): Derives a type-safe SecretKey from the JWT_SECRET byte array, ensuring the key length meets the HS256 minimum (256 bits).

8.7 MySQL 8 and Flyway

MySQL 8.0 with the InnoDB storage engine provides ACID-compliant transaction support, row-level locking for the SELECT … FOR UPDATE pessimistic lock mechanism, and the DECIMAL(19,4) exact numeric type for financial precision. The utf8mb4 character set supports the full Unicode range including emoji, which is relevant for customer name and address fields in multi-language deployments.

Flyway (version 10.x, included transitively by Spring Boot) manages the database schema lifecycle through versioned SQL migration scripts stored in src/main/resources/db/migration/. Each migration file is named with a version prefix (V1__, V2__, etc.), a description, and the .sql extension. Flyway records executed migrations in the flyway_schema_history table, preventing any migration from running twice and detecting checksum changes to already-applied scripts.

8.8 HikariCP

HikariCP is the default JDBC connection pool in Spring Boot, selected for its best-in-class performance characteristics: sub-millisecond connection acquisition, minimal object allocation, and a lightweight codebase. The DigitalBanking application configures HikariCP with a maximum pool size of 20 connections, which is appropriate for a t3.medium EC2 instance running a MySQL RDS instance configured to accept up to 150 concurrent connections.

The pool name DigitalBankingPool is exposed through JMX and Micrometer, allowing pool saturation (waiting connections) and connection acquisition time to be monitored in production dashboards.

8.9 Bucket4j 8.10.1

Bucket4j is a thread-safe, Java-native implementation of the token-bucket rate limiting algorithm, based on the Bucket4j library by Vladimir Bukhtoyarov. The token-bucket algorithm is superior to simpler fixed-window counters for rate limiting because it handles burst traffic gracefully: a client that sends 50 requests at the start of a minute and then pauses will have its bucket refilled for the next burst, rather than being hard-blocked until the window resets.

8.9.1 Application in DigitalBanking

The RateLimitingFilter creates one Bucket instance per client IP, stored in a ConcurrentHashMap. Each bucket has a capacity of 100 tokens and a greedy refill rate of 100 tokens per minute. The Bandwidth.builder().refillGreedy() method fills the bucket continuously throughout the minute rather than adding all 100 tokens at the start of each minute, which prevents coordinated burst attacks at minute boundaries.

Bucket4j 8.10.1 was specifically chosen over earlier versions because it removes the deprecated Bandwidth.classic() constructor and replaces it with the fluent builder API, which is compatible with Java 17 module restrictions.

8.10 Micrometer and Prometheus

Micrometer is the application metrics facade for Spring Boot, analogous to SLF4J for logging. It provides a vendor-neutral API (Counter, Timer, Gauge) that can be backed by any metrics system: Prometheus, Datadog, CloudWatch, New Relic, or others. The DigitalBanking application uses the Prometheus backend via the micrometer-registry-prometheus dependency.

Prometheus scrapes the /actuator/prometheus endpoint at regular intervals (typically every 15 seconds) and stores time-series data. Grafana queries Prometheus to render dashboards showing real-time and historical transaction rates, P99 latency, error rates, and HikariCP pool utilization.

8.11 Testing Technologies

8.11.1 JUnit 5 and Mockito

JUnit 5 (JUnit Jupiter) is the test execution framework providing annotations (@Test, @BeforeEach, @ParameterizedTest), assertions (assertThrows, assertEquals), and extension points. Mockito 5.x provides mock object creation via @Mock, stubbing via when(...).thenReturn(...), and verification via verify(...).

The combination of JUnit 5 + Mockito allows the service layer tests (TransactionServiceImplTest, TransferServiceImplTest, JwtUtilsTest) to run in under 2 seconds without starting a Spring context or connecting to a database. This fast feedback loop enables test-driven development and rapid iteration.

8.11.2 @DataJpaTest and H2

@DataJpaTest is a Spring Boot test slice annotation that starts a minimal application context containing only the JPA layer (entities, repositories, and Hibernate configuration), with all other beans excluded. The H2 in-memory database with MySQL compatibility mode is used as the test database, replacing MySQL to eliminate the dependency on a running database server during testing.

The repository tests (BankAccountRepositoryTest, TransactionsRepositoryTest) verify that JPQL queries, named queries, and lock annotations function correctly against a real relational database (H2), catching issues that pure mocking would miss, such as type mismatch between the Hibernate entity mapping and the underlying SQL.

8.11.3 Testcontainers

Testcontainers is a Java library that provides throwaway Docker containers for integration testing. The DigitalBankingIntegrationTest class starts a real MySQL 8.0 Docker container, runs Flyway migrations against it, and verifies the full application stack including JWT authentication, payment creation, and balance queries.

The integration tests are annotated with @EnabledIfSystemProperty(named="it.docker.enabled", matches="true"), which causes JUnit 5 to skip them when the system property is not set. This allows the standard mvn test CI pipeline to run the fast unit tests without requiring a Docker daemon, while the integration tests can be run separately in an environment with Docker available.

Chapter 9: Conclusion

9.1 Project Summary

This project undertook a comprehensive redesign and improvement of the DigitalBanking Spring Boot backend application, transforming it from a prototype-grade codebase with significant financial correctness, security, and architectural deficiencies into a production-ready banking API that adheres to industry best practices.

The work addressed 87 specific improvement items organised across six phases: financial correctness, architecture, security, database management, testing, and observability. Each phase built upon the previous, ensuring that foundational changes (such as the introduction of BigDecimal and the BankAccount entity) were in place before dependent features (such as pessimistic locking and the transfer service) were implemented.

9.2 Key Technical Achievements

9.2.1 Financial Correctness

The most critical improvements were in financial correctness. The original codebase stored monetary amounts as long integers and derived the current balance from the most recent transaction record — both practices that introduce data loss in production banking systems. The redesigned system stores all monetary values as DECIMAL(19,4) in MySQL and java.math.BigDecimal in Java, with a dedicated bank_accounts table as the single source of truth for the current balance. Race conditions that could cause two concurrent transactions to both read the same balance and produce incorrect results are eliminated through pessimistic write locking (SELECT FOR UPDATE) and optimistic locking (@Version).

9.2.2 Security

The security architecture was rebuilt from scratch: structured JWT claims with issuer and audience validation, BCrypt password hashing, refresh token rotation with server-side revocation, account lockout after five failed attempts, rate limiting at 100 requests per minute per IP, and least-privilege URL-based authorization rules. Sensitive configuration values (JWT secret, database credentials) are externalized as environment variables backed by AWS Secrets Manager in production, never hardcoded in source files.

9.2.3 Architecture

The architectural improvements follow the SOLID principles and clean architecture patterns expected of production Java enterprise applications: constructor injection replaces field injection throughout, domain-specific exceptions replace generic RuntimeException usage, response DTOs replace direct entity serialization, and a global exception handler provides consistent, structured error responses with HTTP status codes, trace IDs, and machine-readable error bodies. The AOP logging aspect provides method-level tracing without the cross-cutting concern polluting business logic.

9.2.4 Testability

The 38-test suite provides coverage at three levels: unit tests for service logic with Mockito mocks, repository tests against H2 in-memory databases with @DataJpaTest, and end-to-end integration tests against real MySQL using Testcontainers. The use of constructor injection (rather than field injection) is what makes the unit tests possible: Mockito cannot inject @Autowired field mocks into a class that requires a running Spring context, but can trivially pass mock objects to a constructor.

9.3 Practical Applications

The patterns implemented in this project are directly applicable to production banking and fintech systems:

  • Idempotency keys are used by Stripe, Razorpay, and virtually every financial API to allow safe client retries. The implementation pattern demonstrated here (check key → process → store response → return) is the canonical approach.
  • Deadlock-safe lock ordering is a standard technique in databases and operating systems. The min-ID-first approach used in the transfer service is equivalent to the algorithm used by database engines themselves to prevent deadlocks during page locking.
  • Token rotation with server-side storage is the recommended approach for refresh tokens in the OAuth 2.0 Security Best Current Practice specification, providing a defence against token theft.
  • Rate limiting with token buckets is the algorithm used by Cloudflare, nginx (limit_req), and AWS API Gateway for request throttling.
  • Flyway migrations are used by companies including Netflix, GitHub, and Atlassian to manage database schema changes in CI/CD pipelines.

9.4 Limitations and Known Constraints

The following limitations are acknowledged and represent areas for future improvement:

9.4.1 Rate Limiting Scalability

The current RateLimitingFilter stores per-IP rate-limit buckets in a ConcurrentHashMap in the JVM heap. This is correct for a single-node deployment but does not distribute rate limit state across multiple EC2 instances in the Elastic Beanstalk Auto Scaling Group. A user could circumvent the limit by having their requests routed to different instances by the load balancer. Production-grade multi-node rate limiting requires a Redis-backed distributed bucket store using the Bucket4j Redis extension (bucket4j-redis).

9.4.2 Spring Cache: Simple Provider

The current cache implementation uses spring.cache.type=simple, which stores cached objects in a ConcurrentHashMap in the JVM heap. Like the rate limiter, this does not share cache state across instances, meaning each instance builds its own cache from scratch. In a multi-node deployment, cache invalidation (when a customer is updated) only clears the cache on the instance that processed the update request. Upgrading to spring.cache.type=redis with a shared ElastiCache Redis cluster would provide consistent cache invalidation across all instances.

9.4.3 HMAC-SHA256 vs RSA JWT Signing

The JWT is signed with HMAC-SHA256 (symmetric), meaning the same secret key is used for both signing and verification. This is appropriate for a monolithic application where only one service generates and verifies tokens. However, in a microservices architecture where different services need to independently verify tokens without having access to the signing secret, RSA (RS256) or ECDSA (ES256) asymmetric signing would be preferable: the private key signs tokens and only the corresponding public key is needed for verification.

9.4.4 Missing Daily and Monthly Transaction Limit Enforcement

The TransactionLimitConfig defines daily and monthly transaction limits (banking.transaction.daily-limit=1000000, banking.transaction.monthly-limit=5000000) but the current service implementation only enforces the per-transaction limit. A complete implementation would require a query aggregating the sum of a customer's transactions within the current calendar day/month before allowing a new transaction, which is omitted from the current scope.

9.4.5 Two-Factor Authentication

Banking-grade security typically requires two-factor authentication (2FA) for high-value transactions or login from a new device. The current implementation provides username/password authentication with JWT but does not implement OTP, TOTP, or push notification 2FA. This is acknowledged as a future enhancement.

9.7 Conclusion

The DigitalBanking project demonstrates that building a production-ready backend for financial services requires careful attention to correctness, security, and observability at every layer of the stack. A working prototype that passes manual testing is not sufficient — a banking system must guarantee that concurrent operations produce correct results, that security controls cannot be bypassed, that failures produce meaningful diagnostics, and that the schema can evolve safely over time without data loss or downtime.

The 87 improvements implemented across six phases address these requirements systematically, each traceable to a specific failure mode or industry best practice. The result is an application that is not merely functional but is demonstrably correct under concurrent load, secure against the OWASP Top 10 threats relevant to API authentication, observable through structured logging and Prometheus metrics, and deployable to production AWS infrastructure with a clear migration path from the development configuration.

The patterns employed here — pessimistic database locking for financial operations, idempotency keys for safe retries, JWT token rotation for session management, Flyway migrations for schema management, and Micrometer metrics for observability — are standard practices in the fintech industry and are directly transferable to real-world banking application development.
