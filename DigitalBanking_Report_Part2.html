Chapter 3  –  Requirement Gathering

This chapter documents the complete set of requirements gathered for the DigitalBanking application through a structured analysis of the problem domain. The requirements are organized into Functional Requirements (what the system must do), Non-Functional Requirements (how well it must do it), User Roles and Use Cases (who interacts with the system and how), and the complete API Feature Set (the precise contract exposed to clients). This analysis preceded all design and implementation activities and directly shaped the architecture of the application.

3.1 Functional Requirements

Functional requirements define the specific behaviors and operations the system must support. For a banking backend, these requirements are derived from the core business processes: account management, financial transactions, authentication, and system administration. Each requirement was assigned a priority level — Mandatory (must be delivered in this project), Important (high value, strongly desired), or Optional (desirable but not blocking).

Table 3.01: Functional Requirements

Req. ID Requirement Description Category Priority
FR-01 The system shall allow a new user to self-register with a username and password via a public endpoint. The password shall be stored using BCrypt hashing and never in plaintext. Authentication Mandatory
FR-02 The system shall authenticate users via a login endpoint and return a signed JWT access token (1-hour expiry) and a refresh token (7-day expiry) upon successful authentication. Authentication Mandatory
FR-03 The system shall support token refresh: given a valid, non-expired refresh token, a new JWT access token and a new (rotated) refresh token shall be issued. Authentication Mandatory
FR-04 The system shall support logout by revoking the user's active refresh token, rendering future refresh attempts invalid without requiring a new login. Authentication Mandatory
FR-05 After 5 consecutive failed login attempts for the same username, the account shall be locked for 15 minutes. Subsequent login attempts during the lock period shall return HTTP 429 with a descriptive message. Authentication Mandatory
FR-06 An administrator shall be able to create, read, update, and soft-delete customer records. Soft deletion shall set is_deleted = true and record a deleted_at timestamp without physically removing the row. Customer Mgmt Mandatory
FR-07 Each customer shall be linked to exactly one bank account record containing a BigDecimal balance, account number, currency (default: INR), and account status (ACTIVE / BLOCKED / FROZEN / CLOSED / DORMANT). Account Mgmt Mandatory
FR-08 The system shall support credit (deposit) and debit (withdrawal) transactions. A debit shall fail with HTTP 422 if the account balance is insufficient. All amounts shall be stored with 4 decimal places of precision. Transactions Mandatory
FR-09 Any credit or debit transaction request may carry an Idempotency-Key HTTP header. If a request with the same key is submitted more than once, the original response shall be replayed without creating a duplicate transaction. Transactions Mandatory
FR-10 The system shall reject any single transaction exceeding ₹5,00,000. A daily cumulative limit of ₹10,00,000 and a monthly limit of ₹50,00,000 shall also be enforced per customer. Transactions Mandatory
FR-11 The system shall support atomic fund transfers between two distinct bank accounts. The source account shall be debited and the destination account credited in a single ACID transaction. If either operation fails, both shall be rolled back. Transfers Mandatory
FR-12 The transfer service shall prevent deadlocks by acquiring database row locks in ascending account-ID order when both accounts are involved in the same transfer, regardless of which is the source or destination. Transfers Mandatory
FR-13 Every committed transaction shall be recorded as an immutable ledger entry with: transaction ID, type (CREDIT/DEBIT), mode (UPI/NEFT/RTGS/IMPS/CASH/CHEQUE/ONLINE), status, amount, balance-before, balance-after, customer ID, and timestamp (Instant precision). Transactions Mandatory
FR-14 An administrator shall be able to reverse a committed transaction by submitting a POST request to /api/v1/transactions/{id}/reverse. The reversal shall create a new offsetting transaction rather than modifying the original record. Transactions Important
FR-15 Transaction history for a customer shall be paginated and filterable by transaction mode (UPI, NEFT, etc.). Transactions Important
FR-16 The current balance of a customer's account shall be retrievable at any time via GET /api/v1/customers/{id}/balance. The balance response shall include currency and account status. Account Mgmt Mandatory
FR-17 The system shall rate-limit all /api/* endpoints to 100 requests per minute per IP address using a token-bucket algorithm. Requests exceeding the limit shall receive HTTP 429. Security Mandatory
FR-18 An admin-only registration endpoint shall allow administrators to create user accounts with assigned roles and optionally link them to a customer record in a single operation. Authentication Important

3.2 Non-Functional Requirements

Non-functional requirements define the quality attributes of the system — the constraints under which it must operate rather than specific behaviors it must exhibit. For a banking system, these are at least as important as the functional requirements, because correctness under load, security under attack, and auditability under scrutiny are non-negotiable properties.

Table 3.02: Non-Functional Requirements

Req. ID Requirement Description Category
NFR-01 Correctness: All monetary arithmetic must use BigDecimal with a minimum precision of DECIMAL(19,4). The system must never derive an account balance from summing or ordering transaction history. Balance is a first-class, directly persisted state in the bank_accounts table. Data Integrity
NFR-02 Concurrency Safety: Concurrent debit operations on the same account must serialize correctly. The system must guarantee that an account balance can never go below zero due to two simultaneous debit requests, even under high concurrency. Concurrency
NFR-03 ACID Compliance: Every transaction that modifies an account balance (credit, debit, or transfer) must execute within a database transaction boundary. Either all changes commit or all roll back. Partial state must never be persisted. Data Integrity
NFR-04 Security — Authentication: All sensitive endpoints must require a valid JWT access token in the Authorization header. The JWT must include issuer, audience, expiry, and roles claims. Passwords must never appear in logs, responses, or configuration files in plaintext. Security
NFR-05 Security — Authorization: Role-based access control must be enforced at the HTTP layer. Admin-only operations (customer creation, transaction reversal, user registration) must return HTTP 403 when attempted by a USER-role principal. Security
NFR-06 Secret Management: The JWT signing secret, database credentials, and all sensitive configuration values must be sourced from environment variables and must not be hard-coded in any file committed to source control. Security
NFR-07 Auditability: Every incoming HTTP request must be assigned a unique Correlation ID (X-Correlation-Id header). This ID must be present in every log line generated during the request's lifetime and returned to the client in the response header for end-to-end traceability. Observability
NFR-08 Observability — Metrics: The application must expose Micrometer counters for transaction.success.count, transaction.failure.count, transaction.insufficient_balance.count, and a transaction.duration timer. These must be accessible at the /actuator/prometheus endpoint. Observability
NFR-09 Database Schema Management: The database schema must be managed exclusively through Flyway version-controlled migration scripts. Hibernate ddl-auto must be set to validate in production — never to update or create-drop. Schema changes must be traceable through Git history. Maintainability
NFR-10 Connection Pool: The application must use HikariCP with a maximum pool size of 20 connections, minimum idle of 5, a connection timeout of 30 seconds, and an idle timeout of 10 minutes to prevent connection leaks in production. Performance
NFR-11 API Response Consistency: All error responses must follow a standard JSON structure containing: timestamp, HTTP status code, error code, human-readable message, request path, and traceId (from MDC). This eliminates client-side guesswork about error formats. API Design
NFR-12 Testability: The service layer must be independently unit-testable without a live database. Repository code must be verifiable using @DataJpaTest with H2. Full-stack integration must be verifiable against a real MySQL instance using Testcontainers. Testability
NFR-13 Immutability of Financial Records: Once a transaction record is committed to the ledger, its amount, type, account, and customer_id must never be modified. Corrections must take the form of reversal transactions, maintaining a complete and tamper-evident audit trail. Data Integrity
NFR-14 Response Codes: The API must use semantically correct HTTP status codes: 200 OK, 201 CREATED, 204 NO CONTENT, 400 BAD REQUEST (validation), 401 UNAUTHORIZED, 403 FORBIDDEN, 404 NOT FOUND, 409 CONFLICT (duplicate), 422 UNPROCESSABLE ENTITY (insufficient balance), 429 TOO MANY REQUESTS (rate limit/lockout). API Design

3.3 User Roles and Use Cases

The DigitalBanking application serves two distinct user roles, each with a different set of permitted operations. The role model is enforced at the HTTP security layer through Spring Security's @EnableMethodSecurity and URL pattern matching rules. A third implicit actor — the System — represents automated background processes such as token expiry and rate-limit counter reset.

Table 3.03: User Roles and Permission Matrix

Role Permissions Spring Security Role
ADMIN Full access to all endpoints. Can create, read, update, and soft-delete customers. Can register new users. Can reverse committed transactions. Can view all transaction history across all customers. Has access to Actuator management endpoints (metrics, prometheus). ROLE_ADMIN
USER Can view their own account balance and transaction history. Can initiate credit/debit payments on their own account. Can initiate fund transfers. Can refresh their JWT token. Can log out. Cannot access other customers' data or admin-only endpoints. ROLE_USER
Anonymous Can access the login endpoint, public-register endpoint, and token refresh endpoint only. All other endpoints return HTTP 401. No role (unauthenticated)

3.4 API Feature Set

The DigitalBanking API follows RESTful design principles with consistent versioning under the /api/v1/ path prefix. All endpoints return JSON. Request bodies that contain domain-specific inputs require a Content-Type: application/json header. Protected endpoints require an Authorization: Bearer <JWT> header. The following tables document the complete feature set grouped by controller.

Table 3.04: Authentication API Feature Set

Method Endpoint Request Body / Parameters Auth Required HTTP Response Purpose
POST /api/v1/auth/login LoginRequest: userName (NotBlank), password (NotBlank, Size 8–64) None (Public) 200 / 401 / 429 Authenticates user. Returns JWT access token, refresh token, userName, roles, customerId. Returns 429 if account is locked.
POST /api/v1/auth/public-register LoginRequest: userName, password None (Public) 201 / 409 Self-registration with ROLE_USER. Returns 409 if username already exists.
POST /api/v1/auth/refresh JSON body: { "refreshToken": "…" } None (Public) 200 / 400 / 422 Exchanges a valid refresh token for a new access + refresh token pair (token rotation). Original refresh token is invalidated.
POST /api/v1/auth/logout None Any JWT 200 / 401 Revokes the caller's refresh token. Subsequent refresh attempts are rejected until user logs in again.
POST /api/v1/auth/register UserRegisterRequest: userName, password (Pattern: uppercase + digit + special char + min 8), roles, customerDetails (optional) ROLE_ADMIN 201 / 403 / 409 Admin creates a new user. Optionally links to a new customer record in a single operation. Returns 409 if username exists.

Method Endpoint Request Auth Response Purpose

Table 3.07: TransactionMode Enum Values and Real-World Use Cases

Mode Value Full Name Description and Typical Use Case
UPI Unified Payments Interface Real-time peer-to-peer payment via VPA (Virtual Payment Address). Used for mobile payments, merchant QR code transactions. Settlement is immediate. Example: Google Pay, PhonePe payments.
NEFT National Electronic Funds Transfer Batch-based fund transfer settled in hourly cycles by the RBI. Used for large-value interbank transfers. No minimum transaction limit. Available 24×7 since December 2019.
RTGS Real-Time Gross Settlement Real-time, individual gross settlement for high-value transactions (minimum ₹2,00,000). Used for corporate treasury operations, property transactions, and time-critical high-value transfers.
IMPS Immediate Payment Service Real-time interbank payment available 24×7 including holidays. Used when immediate settlement is required for amounts up to ₹5,00,000. Faster than NEFT, lower value than RTGS.
CASH Cash Transaction Physical cash deposit or withdrawal at bank branch. Recorded in the system for audit trail purposes.
CHEQUE Cheque Payment Paper-based payment instrument. Subject to clearing cycle (T+1 to T+2 business days). Used for legacy payments and high-value property transactions.
ONLINE Online/Net Banking Transfer Web or mobile banking initiated transfer. Covers card-not-present transactions, bill payments, and e-commerce settlements.

Status Value Description Transition

Key Design Decision — Idempotency Key Header: The payment and transfer endpoints accept an optional Idempotency-Key HTTP header. When present, the system stores a hash of the key along with the serialized response in the idempotency_keys table. If the same key is submitted again (e.g., due to a client retry after a network timeout), the stored response is returned immediately without re-processing. This pattern is used by Stripe, Razorpay, and the RBI's NACH mandate system to prevent duplicate financial operations at the API boundary.
